# UMM + libnvm 真机使用风险分析与测试流程

> 适用范围：当前代码状态（SSD 数据面 = 文件模拟 / libnvm 用户态驱动，双路径）。
> 目标机器：openEuler NPU 服务器（单系统盘 nvme0n1 + libnvm_helper 已加载）。

---

## 一、风险分析（按等级排序）

### 🔴 高风险（执行前必须闭环）

| # | 风险 | 机理 | 对策 |
|---|---|---|---|
| R1 | **"闲置盘"身份未证实** | 真机 `ls /dev/nvme*` 只有 nvme0（系统盘）。被 libnvm 接管的盘从内核消失，`lsblk` 不可见——它是否物理存在、是哪一块，目前只有口头依据 | `lspci \| grep -i nvme` 看 PCI 层有几片盘；与同事 l00835206 书面确认盘的身份（PCI BDF）与可覆写性 |
| R2 | **控制器占用冲突** | `libnvm_helper` use count=3，有进程正在使用。`nvm_host_init` 会复位控制器、重建 admin 队列——若同事进程正在跑实验，其队列被拔、数据损坏 | `fuser -v /dev/libnvm_helper0` 确认无占用；与同事协调时间窗 |
| R3 | **ABI 不匹配（静默 corruption）** | dlopen/dlsym 只校验符号名，**不校验结构体布局**。我们按 `nvm_host.h` 声明的 `nvm_host_disk_info_t`（4 字段）编码，如果真机 .so 的同名结构体布局不同，init 正常但 info 字段全错位 | 跑 Phase 1 冒烟并**人工核对** `get_disk_info` 返回值是否合理（block_size 应为 512/4096，max_data_size 应为 64KB~数 MB 量级）；最好直接 diff 真机头文件与我们依据的版本 |
| R4 | **数据覆写** | 测试/服务写的是裸 LBA。闲置盘上可能有同事 BaM page_cache 的元数据 | Phase 2 用 `UMM_TEST_LIBNVM_OFF` 把写入限定在盘远端；写入前与同事确认该区域空白 |

### 🟡 中风险（测试中观察）

| # | 风险 | 机理 | 对策 |
|---|---|---|---|
| R5 | **buffer 语义未知** | `nvm_host_read/write(void *data)` 是否要求 DMA 注册内存？若要求而我们传 malloc buffer，可能失败或静默错 | Phase 2 的小 IO 回环会直接暴露；若失败，需改用 libnvm 的 DMA 分配接口 |
| R6 | **线程安全未知** | ConcurrentIOEngine 多线程并发调 `nvm_host_read/write`，单 ctx 是否线程安全未证实（queue_depth=64 暗示内部多队列，但需验证） | Phase 4 并发压测 + 数据校验 |
| R7 | **容量语义靠配置** | disk_info 无总容量字段，容量=配置值。配置 > 实际盘容 → LBA 越界 IO 错误甚至卷绕 | 建议同事在 `get_disk_info` 补 NSZE（内部 `nvm_ns_info` 现成）；补上前，容量配置保守取小 |
| R8 | **libnvm 研究代码稳定性** | init 涉及 BAR mmap、队列创建，bug 可能导致内核 oops 或控制器卡死 | INITONLY 先行；出问题时 `echo 1 > /sys/bus/pci/devices/<BDF>/reset` 或重启恢复 |
| R9 | **持久性语义未确认** | `nvm_host_write` 返回 = 落盘还是进控制器缓存？KV 卸载若要崩溃可恢复，需要 flush 语义 | 当前 cache 场景可接受；后续确认 NVMe Flush 支持 |

### 🟢 低风险（知晓即可）

| # | 风险 | 说明 |
|---|---|---|
| R10 | 特权要求 | `/dev/libnvm_helper0` 是 `crw------- root`，umms/测试需 root |
| R11 | `UMM_LIBNVM_PATH` 指向恶意库 | 本机可控环境，风险低；生产部署时固定路径 |
| R12 | 分配元数据易失 | 重启后位图清空、旧数据逐步被覆写——cache 语义正确，勿依赖持久性 |
| R13 | /dev/shm 文件模拟与推理争用 | hisparse 也用 shm，文件模拟盘注意容量规划 |
| R14 | **client 侧 tier 模式未验证** | e2e demo 只走过 CXL(mock) tier；client 通过 tier_router 使用 SSD tier 的配置接线（`ssd_device` 参数）尚未在真机跑通——Phase 3 的重点 |

## 二、测试流程（五阶段，逐级放大）

### Phase 0：信息确认（零风险，不碰盘）

```bash
lspci | grep -i nvme                     # ① 确认第二片盘物理存在，记下 BDF
fuser -v /dev/libnvm_helper0             # ② 确认无进程占用（R2）
ls /home/l00835206/code/NPU_Direct_Storage/build/lib/
diff <(curl -s 我们依据的nvm_host.h) \
     /home/l00835206/code/NPU_Direct_Storage/install/shmem/include/*/nvm_host.h  # ③ ABI 核对（R3）
```
**通过标准**：第二片盘 BDF 确认；helper 无占用；头文件签名一致；同事确认盘可覆写。

### Phase 1：库兼容冒烟（零盘写入）

```bash
export UMM_LIBNVM_PATH=/home/l00835206/code/NPU_Direct_Storage/build/lib/libnvm_host.so
UMM_TEST_LIBNVM_INITONLY=1 \
UMM_TEST_LIBNVM_CTRL="libnvm:/dev/libnvm_helper0@1" \
./bin/test_ssd_libnvm
```
**通过标准**：init/free 成功；**打印的 block_size/max_data_size 为合理值**（人工核对，这是 ABI 正确的直接证据）。
**失败处理**：init 失败 → 检查 ctrl 路径/ns_id/权限/占用；值不合理 → ABI 错位，回到 Phase 0 ③。

### Phase 2：单后端受控写入（写入限定在盘远端）

```bash
# 写入位置限定在 500GB 偏移处（0x7450000000），远离 LBA0 与可能的元数据区
UMM_TEST_LIBNVM_CTRL="libnvm:/dev/libnvm_helper0@1" \
UMM_TEST_LIBNVM_OFF=0x7450000000 \
./bin/test_ssd_libnvm        # 21 项用例
```
**通过标准**：21/21 PASS（小 IO 回环 → R5 闭环；512KB 分段 → 分段逻辑；capacity=0 拒绝）。
**失败处理**：读写 rc≠0 → 大概率 buffer 语义（R5），需改用 libnvm 的 DMA buffer 接口，把报错发回。

### Phase 3：服务级集成（umms + client 全链路）—— ✅ 接线已完成（umm 109b010 / bmpclient 4ce30e6）

R14 已闭环（容器内文件后端 + stub libnvm 后端全链路验证通过）。
一键脚本 `bmpclient/scripts/demo_e2e_ssd.py`（场景 D）自动完成：
生成 umms 配置 → 启动 ummD/umms → client tier_aware 连接 →
enable_ssd（上报 ummD 拓扑 + 本地数据面）→ D0 拓扑校验 →
D1 基础读写 → D2 引擎并发读写校验 + 串行对照。

```bash
export UMM_LIBNVM_PATH=/home/l00835206/code/NPU_Direct_Storage/build/lib/libnvm_host.so
export LD_LIBRARY_PATH=<传递依赖目录>:$LD_LIBRARY_PATH

# 真机：窗口 [1GB, 1GB+16GB)（与 Phase 2 窗口衔接）
python3 bmpclient/scripts/demo_e2e_ssd.py \
    --spec "libnvm:/dev/libnvm_helper0@1+0x40000000" --capacity 16G
```

也可手工起服务（配置模板 `umm/config/umms_ssd_libnvm.yaml`）：
```bash
umm-metadata-service -p 20001 -b 127.0.0.1 &
umm-memory-server -c config/umms_ssd_libnvm.yaml &
```

**通过标准**：D0-D2 全 PASS（2048 条 4KB 并发读写逐字节校验一致）。
**架构事实**：RPC 仅承载分配（umms 的 ssd_pool 是分配权威）；数据面在
client 进程本地（tier_router → transport_ssd → 本地 pool → libnvm），
umms 与 client 各自 nvm_host_init 同一控制器（驱动 1024 qp 容量足够）。
**注意**：真机单 IO ~40-100us，D2 并发加速比应显著 >1（文件/桩环境
单 IO 为亚微秒级 memcpy，加速 <1 属预期，不作为判据）。

### Phase 4：并发与稳定性（性能基线）

- ConcurrentIOEngine 8 线程并发读写 + 全量数据校验（R6 闭环）；
- 反复 init/free 50 次（句柄/内存泄漏）；
- 30 分钟 soak（混合读写）；
- 记录吞吐/IOPS 基线，与文件模拟路径对比。
