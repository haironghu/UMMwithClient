# 盘内逻辑排布与读并发实验

本实验固定八盘 `(原始 layer_id, token)` 位置哈希，关闭读合并，仅改变盘内逻辑布局和主机读线程数。需要同步包含 `--experiment layout-concurrency` 的代码到服务器；旧脚本不支持该选项。

## 实验矩阵

| 参数 | 设置 |
| --- | --- |
| 盘内布局 | ordered：按 token 顺序插入；shuffled：固定随机种子打乱插入顺序 |
| 读线程总数 | 1、4、8、16；不是每盘队列深度 |
| 准备写粒度 | 两种布局均用 1 MiB 聚合段，不加入 4 KiB 小写基线 |
| 读请求 | 每个 trace token 一个 4 KiB 槽位读，保留重复 token，不合并 |
| 回放模式 | snapshot：全量准备、刷盘完成后再读 |
| 重复次数 | 默认 3，共 2 × 4 × 3 = 24 轮 |

同一布局跨读线程数保持地址映射一致。每轮都会重新准备数据，尚未实现准备一次复用所有读实验。日志分别显示准备、flush/sync 和回放进度；准备进度含内存缓冲中的行，不等于设备已完成写入量。

这里控制的是 LBA 排列，不能证明 token 落到指定 die/plane。shuffled 是合成对照，不代表生产环境已有排布。

## 服务器执行

在项目根目录运行，trace 使用 CSV 转换后的 JSONL。容器需要已映射八块设备，且原生 SSD pool 库已编译成功。先查看计划（不打开或写设备，也不创建输出文件）：

```bash
mkdir -p results
python3 bmpclient/scripts/bench_layout_replay.py \
  --trace traces/real_trace.jsonl \
  --devices-config bmpclient/bench/eight_devices.huawei.json \
  --output results/layout-workers.json \
  --experiment layout-concurrency \
  --segments 1M --worker-sweep 1 4 8 16 --repeats 3 \
  --dry-run
```

实际测试将末尾 `--dry-run` 替换为 `--allow-device-write`，会覆盖配置指定设备窗口内的数据。该配置对应已授权的 `/dev/nvme80n1a` 至 `/dev/nvme87n1a`。输出路径必须尚不存在。

首次可用短 trace、`--worker-sweep 1 4 --repeats 1` 验证，共四轮。正式比较应保持 trace、种子和其他参数一致。此模式强制禁用读合并，不需要再加 `--no-merge`；`--max-read-bytes` 不用于合并。读并发使用 `--worker-sweep`，而非旧的 `--workers`。

## 结果解读

- `trials[].fetch_us`：逐批（一个 step/layer）读取延迟分位数；`active_fetch_seconds`：全部批次读取时间之和。
- `effective_unique_kv_MiB_s`：按唯一 token 的有效 KV 字节计算吞吐；`io.devices`：每盘原生 I/O 统计。
- `comparisons`：同线程数下 shuffled 对比 ordered；同布局下最小线程数对比更高线程数。`median_fetch_speedup` 为基线读取总时长中位数除以候选值，大于 1 表示候选更快。
- `mapping_sha256`：检查同布局在不同线程数下的映射一致性；`worker_sweep` 和每轮 `workers` 记录实际并发配置。

准备、刷盘和数据校验不计入 fetch 时间。fetch 包含 Python 调度、内部查表、内存分配和原生对齐拷贝，首次读取还包括线程池启动；不清空 SSD 固件缓存。结果用于比较当前主机回放路径，不能直接当作真实模型 TPOT 或纯设备延迟。

原有写粒度实验保留在默认 `--experiment write-layout` 下。进行本实验必须显式指定 `layout-concurrency`。

## 数据校验失败

遇到 `data mismatch` 时测试终止，结果标记为 `failed`，不能用于性能结论。
`active_trial` 记录失败轮次；`failure` 保存 step/layer/token、设备路径、盘内字节偏移、
首个不同字节的位置以及期望/实际数据摘要。清理前会绕过批量读取路径，直接进行一次原生重读，
结果记录在 `failure.native_retry`，不执行修复性写入。

重读正确提示需要检查批量读取、输出缓冲或瞬态问题；重读仍错误则需继续检查写入、地址映射、
其他写入者及存储路径，不能据此直接判定坏盘。诊断重读仅发生在失败时，不计入成功试验指标。
保留失败 JSON 和日志，再安排复现；不要使用 `--no-verify` 绕过错误。

### 跟踪指定页的准备写入

在原命令增加 `--watch-device-offset 0 2200104960`，分别指定设备索引和设备内绝对字节偏移。
地址须 4 KiB 对齐且位于配置窗口内，仅支持 snapshot。
保持 trace、种子和 segment 不变，先用 `--worker-sweep 1 --repeats 1` 复现，并换新的输出文件名。

此选项不增加写入，只在正常准备写覆盖目标页时，立即原生读回该页，与写缓冲中的对应内容比较；
全量准备和刷盘结束后再检查一次。日志 `write-watch` 和 JSON `write_watch` 保存结果：

- `immediately_after_write` 为 `mismatch`：写调用返回后就不一致，立即停止准备。
- 立即检查 `matched`，`after_snapshot_sync` 为 `mismatch`：该页在后续准备过程中发生了变化。
- `not_written`：这轮未观察到覆盖目标页的写调用，需要检查目标地址和写入范围。
- 两次均 `matched` 而回放仍失败：继续比对回放期望摘要、地址映射及错误发生时间。

错误数据不能直接证明坏盘。该诊断会影响 I/O 统计与缓存状态，不用于正式性能比较。

### 精确 super page 大小

段大小现支持任意满足 4 KiB 和槽位大小对齐的正整数，不再限定为 2 的幂。
按当前几何假设 `1626 × 16 KiB`，使用 `--segments 26640384`，即 25.40625 MiB，
每段 6504 个 4 KiB 槽位。这个大小不保证物理 plane 均匀分布。

同步新版 Python 代码后，在原命令中把 `--segments 1M` 替换为上述参数，并换新的输出文件名。
固定相同 trace、seed、布局、读线程数和重复次数，与原先 1 MiB 结果比较。
读取指标仍为 `fetch_us`、`active_fetch_seconds`；尾段补零量可能随段大小变化，
多个请求的 extent 起点也可能变化，不能自动认为所有组的绝对 LBA 完全一致。

新增 `trials[].write_call_us`（p50/p95/p99）、`write_call_count` 和 `write_call_total_ms`，
记录每个聚合段调用原生写接口的耗时。包含原生对齐拷贝，不含生成数据、填充聚合缓冲及随后的 sync，
也不代表断电持久化时延。尾部补零段也按完整段写入并参与统计。每次实际写请求仍可能被驱动拆分。
`flush_sync_ms` 包含尾段写入与同步，不是纯同步耗时，不能与全部写调用时间直接相加。

读回全零问题尚未定位时，`--no-verify` 结果只能用于未校验的性能摸底；正式性能对比关闭写入跟踪。
