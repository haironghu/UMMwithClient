# 盘间分盘策略对照

现有对照为 hash、range、stripe、layer，移除 sequential 与 --sequential-device-bytes。
固定 ordered 盘内布局、相同 trace、聚合写大小、读线程数及 seed，关闭读合并。

| placement | 分盘规则 |
| --- | --- |
| hash | 原有 (原始 layer_id, token) 位置哈希 |
| range | 每个 request/layer 按最大上下文长度将 token 连续均分到八盘；前面余数个盘各多一个 token |
| stripe | 每层从 SSD0 开始，每 stripe_rows 个 token 换盘，盘号 = (token // stripe_rows) % 8 |
| layer | 一整层放一盘，盘号 = 原始 layer_id % 8；所有请求使用相同规则 |

range 与 stripe 暂限八盘 snapshot，均在每层重新从盘 0 计算，不按写入先后分配盘号。
layer 也暂限八盘 snapshot；使用原始模型层号，不是 trace 中压缩后的层编号。
因此即使启用 shuffled 盘内布局，同一个 token 的盘号也不变。
range 使用 snapshot 最大上下文长度，不能直接作为随 decode 增长而不断重分区的在线策略。
stripe 在上下文长度不足一轮条带时可能只使用部分盘，长上下文的尾部也可能不均衡。

`--stripe-bytes` 默认 1 MiB，按 4 KiB 槽位计算，默认每 256 个 token 换盘；
这是逻辑分盘条带大小，与 `--segments` 的聚合写请求大小独立，不是 NAND 物理条带。
例如 `--stripe-bytes 1M --segments 26640384` 表示每 256 个 token 换盘，
每盘积累 6504 个槽位后提交一次 25.40625 MiB 聚合写。
三组保留每请求尾段补零及空盘 extent，实际写入量需结合 io.devices 查看。

## 启动

同步新版代码，在项目根目录执行，替换 trace 路径。先用 --dry-run 查看规划（不打开设备）：

```bash
mkdir -p results
for placement in hash range stripe; do
  python3 -u bmpclient/scripts/bench_layout_replay.py \
    --trace traces/real_trace.jsonl \
    --devices-config bmpclient/bench/eight_devices.huawei.json \
    --output "results/placement-${placement}.json" \
    --experiment layout-concurrency \
    --placement "$placement" --layouts ordered \
    --stripe-bytes 1M --segments 26640384 \
    --worker-sweep 1 4 8 16 --repeats 1 \
    --no-verify --dry-run \
    > "results/placement-${placement}.log" 2>&1 || break
done
```

实际运行将 --dry-run 替换为 --allow-device-write，将覆盖已授权的设备窗口。
不要同时运行三组；输出 JSON 须不存在。正式测量使用更多重复，并反转策略执行顺序复测。
--stripe-bytes 仅在 stripe 组生效；其他组 JSON 的 stripe_bytes 为 null。
当前 --no-verify 仅用于未校验性能摸底，读回全零问题解决后应启用校验复测。

## 指标与收益

沿用 fetch_us、active_fetch_seconds、effective_unique_kv_MiB_s。
每个 trial/batch 的 io.devices 可检查每盘读次数和字节数，避免只看全程总量掩盖单批负载不均衡。
每个文件的 comparisons 仍是文件内的线程数/布局比较，不是跨策略结果。
相同线程数、相同段大小下：

- hash 相对 range 加速倍数 = range 读取总时长中位数 / hash 读取总时长中位数。
- hash 相对 stripe 加速倍数 = stripe 读取总时长中位数 / hash 读取总时长中位数。

大于 1 表示 hash 更快。比较前确认 trace_sha256、seed、segments、worker_sweep、repeats、
layouts、merge、verified、设备窗口和原生库版本一致。三组的尾段补零及 extent 基址可能不同，
不能宣称仅由结果证明 NAND plane 更均匀；这里测量的是主机可控的分盘策略效果。

## 整层轮转对照（vLLM block_size=32）

layer 0 的所有 block 放 SSD0，layer 1 放 SSD1，……，layer 8 再追加到 SSD0。
ordered 写入时，每层按 token 顺序追加，因此该层逻辑 block 顺序也保持不变。
同一 block 的 32 个 token 不跨盘，但当前 6504 槽位的 super page 不是 32 的整数倍，
允许一个 block 跨聚合写请求；不增加 block 尾部填充或改变写入粒度。
这只是逻辑分盘对照，并非复刻实际 vLLM 张量的物理 stride 或整块搬运成本。

```bash
python3 -u bmpclient/scripts/bench_layout_replay.py \
  --trace traces/real_trace.jsonl \
  --devices-config bmpclient/bench/eight_devices.huawei.json \
  --output results/superpage-layer-r1.json \
  --experiment layout-concurrency --placement layer --layouts ordered \
  --vllm-block-size 32 --segments 26640384 \
  --worker-sweep 8 16 --repeats 1 --no-verify --dry-run
```

确认计划后，以 --allow-device-write 替换 --dry-run 进行实际测试。
`--vllm-block-size` 只记录实验元数据，不改变分盘、读取粒度、段大小或填充方式。
当前逐 batch/逐层回放，所以 layer 策略每批只有一盘接收读请求；多个线程可以并发读这同一盘，
不能把层轮转理解成八层同时执行。对比 hash 时保持 trace、写段大小、布局和线程数一致。
