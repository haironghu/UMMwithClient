# 八盘哈希分盘与盘内排布回放

当前目标是使用八块 SSD，跨盘使用现有 position_hash，盘内比较顺序/打乱排布与小写/聚合写。没有接入聚类。旧单盘命令继续可用，八盘使用 `--devices-config`，与 `--file`、`--device` 互斥。

## 配置八个获准窗口

复制 [eight_devices.example.json](../bench/eight_devices.example.json) 为自己的配置，逐项填入管理员给出的起点和长度。模板按之前设备列表填写 `/dev/nvme80n1a` 至 `/dev/nvme87n1a`；运行前必须核实设备对应关系。模板中的 null 故意不能运行，不会默认选择整盘。

每项格式如下（这是字段说明，不是授权范围）：

```json
{"device":"/dev/获准设备","window_offset":"获准起点字节数","window_bytes":"获准长度字节数"}
```

整个文件是恰好八项的 JSON 数组。数组第 0 项注册为 UMM 设备 0，第 7 项注册为设备 7；不是将 Linux 名称中的 80～87 直接作为盘号。顺序改变会改变 token 到物理盘的映射。

- 每盘独立的 window_offset/window_bytes，可以不同，必须是 4096 B 的倍数。
- 可填整数（字节）或 `1M`、`4G` 等二进制容量字符串。起点是设备节点内的相对字节位置；传入分区时相对于分区。
- 必须提供绝对路径。不允许重复路径或解析后相同的符号链接；实际执行还检查重复块设备号。
- 不能据此识别同一物理盘的多个 namespace、不同分区或多路径别名。八项是否对应八块独立获准 SSD 仍需管理员确认。
- 文件中只接受 `device/window_offset/window_bytes` 三个字段。开发验证也可使用 `file` 替代 device 指向八个新普通文件，不能在同一配置混用两种类型。

## 只预览，不打开设备

先完成 CSV 到 JSONL 的转换，再执行：

```bash
python3 bmpclient/scripts/bench_layout_replay.py \
  --trace /data/traces/real_trace.jsonl \
  --devices-config /data/config/eight_devices.json \
  --output /data/results/eight-layout.json \
  --mode snapshot --segments 64K 1M \
  --workers 8 --repeats 3 \
  --dry-run
```

`--dry-run` 读取 trace 和配置，计算每盘容量，输出计划到终端；不打开设备、不加载 SSD 后端、不创建结果文件。结果路径必须尚不存在。它不验证实际设备容量、占用、权限或 O_DIRECT 支持。

操作者确认配置后，用相同命令将 `--dry-run` 替换为 `--allow-device-write` 才执行真实写入。不格式化、不创建文件系统、不 discard，也不选择默认写窗口。实际设备大小、对齐、独占打开由原生后端检查；八盘必须全部成功打开才开始 trial。

在线追加模式改为 `--mode online`；每批读取前 flush，段尾填充可能显著增加每盘容量需求。参数变化后重新预览。

## 哈希与逐盘容量

沿用 PositionHashStrategy 的默认参数：

```text
盘号 = ((token * 17 + 原始模型 layer_id * 23) % 2147483647) % 8
```

内部槽位表仍可以压缩 layer 编号，但写入、plan、fetch 和 release 使用的策略会将其映射回原始模型 layer_id。请求 ID 不参与哈希；不同请求的相同 layer/token 落在相同编号的盘，在不同 extent 内隔离。

容量不按总数据量简单除以八。预览逐个计算新增 token 的目标盘：

- snapshot：按 request 聚合每盘 token 数，再按最大候选段补齐。
- online：按每次新增范围分别计算各盘 token 数和 flush 填充，再累计。
- 每个 request 在每盘至少预留一个段，即使没有 token 落在该盘，以适配 VirtualMedia 的每盘 extent 生命周期；空盘预留不产生虚假数据写入。
- 每盘采用所有请求需求之和的保守上界；各对照组使用相同预留容量。请求退出后真实释放 extent，后续请求可以复用。

若某一盘的窗口不足，指出盘号与最小所需字节数并拒绝执行；不会自动把数据换到别的盘。不同盘的 token 数可能不完全相等，top-k 的读负载也不保证均衡。

## 输出与测试

结果 schema_version 为 2，包含：

- `devices[]`：盘号、设备路径、授权窗口、逐盘容量需求及可能写入范围 `[start,end)`。
- `rows_per_request_device`：每个请求的 token 在八盘上的数量。
- `hash_strategy`：哈希参数和原始 layer 语义。
- `trials[].io.devices[]`：逐盘实际成功读写调用数、字节数、对齐中转字节数。
- `trials[].batches[].io.devices[]`：每批的逐盘读取统计；顶层 io 为八盘求和。
- 原有整体 fetch 延迟、有效 KV 带宽、plan 时间及对照 speedup 保留。整体批次耗时是等待所有读完成的时间，不是八盘延迟之和。

不同盘上的同步 pread 由同一个 ConcurrentIOEngine 并发调度；workers 是总工作线程数，不是每盘线程数或硬件 QD。写侧仍为主机顺序追加、各盘段缓冲聚合，同步时逐盘 fdatasync。没有新增并行写流水线。

基准适配层现在提供真实 extent 地址解析：plan 输出的是指定设备内 `window_offset + extent_device_offset + token_offset`。CPU fetch 仍通过 descriptor 和原生池路由；现有普通 UMMLib 若不提供该解析器，生产直通地址导出依旧未补齐，不能将本次修正理解为 NPU 链路已可用。

开发验证命令：

```bash
UMM_TEST_DIRECT=1 python3 -m unittest bmpclient.tests.test_multi_device -v
```

测试只用 `/tmp/umm-eight-*` 中的八个普通文件，覆盖 snapshot/online、不同窗口起点、原始 layer 哈希、多请求释放、两轮倒序、逐盘统计总和及窗口外字节未变化。其他测试覆盖缺盘、重复路径、单盘容量不足、dry-run 不打开目标、申请中途失败回收已分配 extent。没有访问真实 NVMe 设备，不代表八块独立物理 SSD 的性能结论。
