# 真实排布路径回放与实施计划

本轮目标是在没有 GPU/NPU 的开发环境完成可运行的真实排布路径测试。开发验证只使用普通临时文件或模拟接口；支持由操作者显式指定裸设备覆盖窗口。不访问用户 NVMe 设备，不操作服务器、不修改文件系统或盘配置。

## 实施计划与交付

| 步骤 | 验收条件 | 交付 |
|---|---|---|
| 1. 接入真实排布路径 | offload、段聚合、槽位页表、plan/fetch、release 均实际执行 | `bench/layout_replay.py` |
| 2. 补齐实验对照 | 数据相同、读策略相同，分别比较排布顺序和分段大小 | ordered/shuffled × 4 KiB/候选段大小 |
| 3. 转换外部 trace | 支持字段映射、JSON/JSONL、纯 token 列表；缺失必要信息拒绝猜测 | `scripts/convert_kv_trace.py` |
| 4. 在线回放 | 追加增长的 KV、读取前 flush、请求结束释放，报告填充成本 | `--mode online` |
| 5. 验证与运行说明 | 多请求、重复 token、原次序、回收、读合并边界、文件保护 | `tests/test_layout_replay.py` 与本文 |

读调度目前沿用 ConcurrentIOEngine，其已有按 worker 分组提交逻辑。迁移到 C 或引入异步 I/O 需要先确认主机调度确实成为瓶颈，不在本轮强行更换。多盘聚类、模型执行及 NPU 数据面不属于本轮。

## 两个基准的区别

- `bench_single_ssd.py`：前一轮 SSD pool 微基准；固定槽偏移，使用主动对齐缓冲，比较写粒度，详情见 [09 指南](09_单盘直接IO与trace回放.md)。
- `bench_layout_replay.py`：本轮新增；使用实际 SparseKVStore 和 VirtualMedia，真实插入顺序决定槽位表偏移，覆盖主机回放链路。

新路径为：

```text
KVBlockRef → SparseKVStore.offload → VirtualMedia/DeviceSegmentManager
           → PoolClient（基准适配层）→ libumm SSD pool → O_DIRECT 文件
SparseKVStore.plan → 检查磁盘 descriptor 与槽位地址
SparseKVStore.fetch → VirtualMedia.read_batch → ConcurrentIOEngine → 同一 SSD pool
SparseKVStore.release → 段回收 → close → 原生 extent free
```

PoolClient 只是将 UMMLib 的拓扑、extent 和 buffer 接口接到真实原生 SSD pool：每个 extent 都调用 `ssd_pool_alloc_on_device/free`，没有用 FakeUMMLib。它不经过 UMM 的元数据服务、RPC 或 `umm_alloc_on_device` 高层 API；后者的文件后端测试仍由 `make -C umm test-direct` 覆盖。不能把这个基准当成完整生产部署测试。

每个 request 拥有自己的 SparseKVStore、VirtualMedia，并在每个已注册设备上分别申请 extent，避免原槽位表没有 request 维度导致不同请求混淆。外部稀疏 layer 编号在槽位表内映射为稠密编号；哈希分盘和 JSON 仍使用原始模型 layer 编号。本轮没有改变生产请求管理接口。

## 编译与验证

在仓库根目录：

```bash
make -C umm -j4
export UMM_BUILD_DIR="$PWD/umm/build"
python3 -m unittest bmpclient.tests.test_layout_replay -v
```

普通单测不写真实 SSD 后端。要在开发机普通临时文件上执行原生 O_DIRECT 集成测试，显式运行：

```bash
UMM_TEST_DIRECT=1 python3 -m unittest bmpclient.tests.test_layout_replay -v
```

集成测试仅新建 `/tmp/umm-layout-test-*` 内的普通文件并在结束后删除；要求 `/tmp` 文件系统支持 O_DIRECT。它覆盖 snapshot/online、双轮倒序、三请求交错与 extent 复用、重复 token 校验以及重复运行拒绝覆盖。

## 外部 trace 转换

标准字段定义沿用 [09 指南](09_单盘直接IO与trace回放.md)。工具不猜测 token 属于哪个 request、layer 或上下文；输入下标必须是 request 内 token 下标，不能是 vLLM 物理 block ID。

### CSV：step_idx, layer, step_seqlen, idx_0, …, idx_2047

支持带表头的逗号分隔 UTF-8 CSV（兼容 UTF-8 BOM、CRLF）。一份 CSV 对应一个请求，通过 `--request-id` 指定：

```bash
python3 bmpclient/scripts/convert_kv_trace.py \
  --input /data/traces/real_trace.csv \
  --output /data/traces/real_trace.jsonl \
  --format csv --request-id r0
```

| CSV 列 | 输出 JSONL 字段 |
|---|---|
| `step_idx` | `step_id` |
| `layer` | `layer_id` |
| `step_seqlen` | `context_length`，直接作为 token 数量，不加减 1 |
| `idx_0` … `idx_2047` | `topk_token_indices`，按列编号数值顺序组装 |
| 命令行 `--request-id` | `request_id` |

转换后把 JSONL 路径传给回放脚本的 `--trace`。每一 CSV 数据行保持为一条回放记录，不重新排序 step/layer，不排序或去重 token。CSV 的物理列顺序可以不同，列名必须正确且不重复。

默认要求恰好 2048 个 idx 列及 3 个元信息列；小规模测试可用 `--max-topk N` 要求 `idx_0..idx_(N-1)`。每个单元必须是非负十进制整数，step_seqlen 必须大于 0，所有 idx 必须小于 step_seqlen。空值、NaN、浮点写法和 `-1` padding 会报错并指出行/列，不自动过滤或转换。该 CSV 格式不使用 `--field`、`--layer-id`、`--context-length` 或 `--step-start` 覆盖已有元信息。

若 CSV 混合了多个请求，仅凭现有列不能区分请求，应先按请求拆分；不同文件使用不同 request-id。转换工具只读 CSV、写新的 JSONL，不打开 SSD 后端或块设备。

### JSON / JSONL

假设外部 JSONL 每行类似：

```json
{"req":"r0","step":0,"layer":2,"ctx":8192,"ids":[17,3,4000]}
```

转换命令：

```bash
python3 bmpclient/scripts/convert_kv_trace.py \
  --input /data/traces/export.jsonl --output /data/traces/normalized.jsonl \
  --field request_id=req --field step_id=step --field layer_id=layer \
  --field context_length=ctx --field topk_token_indices=ids
```

如果输入是整个 JSON 数组而非 JSONL，添加 `--format json`。只支持平面字段映射，不自动解析嵌套张量或模型特定格式。

如果只有每行一个 token 列表，例如 `[1,7,90]`，可以显式补充元信息：

```bash
python3 bmpclient/scripts/convert_kv_trace.py \
  --input /data/traces/token_lists.jsonl --output /data/traces/normalized.jsonl \
  --request-id r0 --layer-id 0 --context-length 32768 --step-start 0
```

缺少 step_id 时按有效记录次序生成 step_start+i；输入中已有字段优先，默认值只补缺失项。固定 context_length 只适用于确实固定的上下文；在线增长应在原记录中提供逐批 context_length。工具保留重复 token 及原顺序，调用与基准相同的校验器，输出 trace/source SHA256 和记录数。输出必须是新文件，非法 trace 不生成最终文件。

## 快照排布实验

普通文件模式使用 `--file`，必须是新文件。裸设备使用下节的显式窗口参数。以下路径是占位符，应由操作者在确认的测试目录中自行执行；本文不会选定或访问你的 NVMe 盘。

```bash
python3 bmpclient/scripts/bench_layout_replay.py \
  --trace bmpclient/bench/traces/example.jsonl \
  --file /mnt/test-ssd/layout-snapshot.raw \
  --output /mnt/test-ssd/layout-snapshot.json \
  --mode snapshot --segments 64K 1M --workers 4 --repeats 3
```

工具先写入每个 request/layer 的最大 context_length，之后按原 trace 顺序回放。每组候选段大小自动加入 4096 B；对每种大小同时运行 ordered 和 shuffled。奇数轮倒转全部方案顺序。

- ordered：在本次追加范围中按 token 顺序插入真实 store。
- shuffled：固定种子打乱本次追加范围，改变真实槽位映射；不是读取时临时乱序，也不是来自原生产系统的布局。
- 所有方案使用同样的单 token KVBlockRef 入口、伪随机数据模式、读合并上限、并发数和 trace。文件大小、每个 request 的预留 extent 容量也相同。
- snapshot 的插入范围是整个 request/layer；online 的插入范围仅为本批新增 token，不能重排已经卸载的历史 token。
- 段尾填充量和写入字节数可能不同，按真实结果报告，不用额外写入人为抹平差异。未使用的文件区域不进入读取。

真实 VirtualMedia 要求段大小为 **2 的幂**，因此新脚本不接受 26,640,384 B。该数值仍可用于旧 SSD pool 微基准；本轮没有放宽生产段管理器使用位移寻址的几何约束。先用 1/4/16/32 MiB 等合法候选评估。

`--max-read-bytes` 限制连续合并的最大长度；`--no-merge` 关闭合并，其他读策略保持一致。两个参数接入真实 VirtualMedia，原调用者不指定时保持旧行为。现有真实 read_batch 不保证重复 token 去重，实际读字节与调用数按原生统计报告，因此不要将它与旧微基准的去重 I/O 数直接比较。

## 在线追加、flush 与释放

```bash
python3 bmpclient/scripts/bench_layout_replay.py \
  --trace /data/traces/normalized.jsonl \
  --file /mnt/test-ssd/layout-online.raw \
  --output /mnt/test-ssd/layout-online.json \
  --mode online --segments 64K 1M --workers 8 --repeats 5
```

在线模式要求同一 request 的 step_id 不递减、同一 request/layer 的 context_length 不缩短。每次读取前追加尚未卸载的 token，然后 flush 并同步，检查 plan 的每条 descriptor 是磁盘地址。不会用未下盘缓冲命中冒充 SSD 读取提升。

请求最后一条 trace 记录完成后释放其所有槽位，检查全部段可回收，再关闭介质释放 extent。生命周期终点来自最后一次读取，**不是**外部模型的显式完成时间。请求 ID 不得跨生命周期复用；此版本不模拟中途淘汰、重新加载、异步 flush 或模型计算重叠。

当前生产段管理器半满段也整段写出，而且显式 flush 后下次追加分配新段。每次追加 1 token 就 flush，在 1 MiB 段上会有很大的写放大和容量成本。基准据各次增长量向上取整计算保守容量并报告，不隐藏该行为。它可用于决定后续是否需要部分段持续追加或不同 flush 策略；本轮没有改变这些生产语义。

## 指标与比较

结果 JSON 的 `status` 必须是 `complete`；运行中逐个保存 trial，失败记录 error。结果包含系统架构/内核、库与 trace 哈希、文件容量、各请求 extent 容量和所有实验参数。

| 指标 | 解释 |
|---|---|
| `mapping_sha256` | 实际槽位表中 request/layer/token/offset 的摘要，用于重复实验检查确定性 |
| `plan_us` | 真实 descriptor 规划耗时，检查工作在计时外 |
| `fetch_us` / `active_fetch_seconds` | 真实 fetch 的批延迟分位数 / 批耗时之和 |
| `append_ms` | 数据生成、KVBlockRef、槽位更新及追加触发的自动整段写时间 |
| `flush_sync_ms` | 显式 flush 与 fdatasync 的时间 |
| `release_ms` | 槽位/段释放、引擎关闭与 extent 回收时间 |
| `io` / `batches[].io` | 原生成功调用数、实际传输字节与对齐中转字节；分别为整轮/该批 fetch |
| `write_amplification_vs_slots` | 实际写字节 / 新增 token 数 × 4096 B（分母按乘积计算） |
| `read_amplification_vs_unique_kv` | 实际读字节 / 去重后有效 KV 字节（每 token 1152 B） |
| `effective_unique_kv_MiB_s` | 去重有效 KV 字节 / 活跃 fetch 时间，不包括写入、校验和释放 |
| `comparisons` | 相同段大小比较顺序、相同顺序比较段大小，以及组合方案对 shuffled 4K 的比较 |

`median_fetch_speedup` 是基线总 fetch 时间中位数 / 候选中位数，大于 1 表示候选更快；`paired_speedups` 保留逐轮比值。分别观察 ordered vs shuffled、同布局 4K vs 大段，避免把读合并收益都归因于写聚合。

plan 和 fetch 分开测量，fetch 内部会再次做槽位查询，所以不能将二者简单相加作为生产流水线延迟。默认数据逐批校验在计时外；`--no-verify` 可在正确性验证后另跑，所有方案应采用相同设置。

真实 VM 的 bytearray 可能不满足 O_DIRECT 指针对齐要求，所以原生中转复制在计时内，`bounce_bytes` 如实报告，**不要求为零**。这与主动对齐的旧微基准不同。fetch 还包括 Python 分配、并发提交、拼接复制，首批可能包含懒创建线程；没有预热或 SSD 缓存清除。小样例只做功能验证，真实性能应使用足够多的批次、多种 trace 和重复轮次。

连续文件偏移、连续 LBA 和 NAND die 分布是不同层次；本实验不控制 FTL，不能直接证明 die 并行度或模型 TPOT 改善。两个基准均未在本轮访问你列出的 NVMe 盘。


## 裸设备指定区域回放（无需文件系统）

真实排布回放现支持 `--device`，与 `--file` 互斥。采用现有 O_DIRECT 后端，在指定窗口内分配 extent；不创建文件系统，不预分配文件、不截断或格式化设备。

需要管理员提供三个精确值：设备路径、可覆盖区间起点、区间长度。起点和长度均为**字节**，必须按 4096 B 对齐；起点相对于传入设备节点（传入分区则相对于分区）。允许区间为 `[offset, offset + bytes)`，右端不包含。不要把结束地址填成长度。

先设置操作者确认的参数，再做不打开设备的容量预览：

```bash
# DEVICE、OFFSET、BYTES 须由操作者按获准区间设置；无默认盘或默认范围。
python3 bmpclient/scripts/bench_layout_replay.py \
  --trace /data/traces/real_trace.jsonl \
  --device "${DEVICE:?请设置获准设备}" \
  --window-offset "${OFFSET:?请设置窗口起点字节数}" \
  --window-bytes "${BYTES:?请设置窗口长度字节数}" \
  --output /data/results/layout-result.json \
  --mode snapshot --segments 64K 1M --repeats 3 \
  --dry-run
```

`--dry-run` 输出 JSON 到终端，不创建结果文件、不加载后端、不打开目标设备，不检查真实设备大小、占用或 O_DIRECT 支持。需要提供一个尚不存在的 output 路径。它报告：

- `capacity_bytes`：根据 trace、模式和最大段计算的本次 extent 总需求。
- `window_offset/window_bytes`：操作者指定的授权窗口。
- `possible_write_range`：窗口开头可能写入的 `[起点, 终点)` 字节范围；并非每个字节都一定写到。
- `request_capacities`：每个请求预留容量，在线模式包括各次 flush 的填充成本。

窗口不足、未对齐或发生 64 位偏移溢出时，预览也会报错。改变 trace、mode 或 segments 后重新预览。

由操作者确认后，使用同一命令将 `--dry-run` 替换为 `--allow-device-write` 才会真正打开和写入设备。每次运行都必须显式给出窗口；仅设置环境变量不能绕过命令行覆盖开关。块设备大小、逻辑扇区和窗口范围由原生后端再次检查；设备独占打开失败时直接失败，不降级访问。

底层使用 O_EXCL，不能代替管理员确认厂商存储软件的占用关系。此基准为单进程单池，不涉及多个 UMM 服务重复独占打开同一设备。CPU 数据调用使用池虚拟偏移，后端统一加上 window_offset；基准 plan 的 descriptor 通过适配层解析为设备内绝对字节地址（已经包含 window_offset），不要再加起点。旧 UMMLib 未提供解析器时仍保留占位行为，不应将其用于直通。

裸设备入口测试使用模拟的块设备类型和后端打开函数，校验参数保护、窗口传递、环境变量恢复和错误结果保存；没有创建或打开真实块设备。原生窗口读写保护此前已通过普通文件测试，真实设备兼容性与性能需要现场验证。CSV、JSONL 和结果文件仍放在主机已有可写目录中，KV 数据直接读写裸设备窗口。


八盘哈希分盘实验及配置文件见 [11_八盘哈希回放.md](11_八盘哈希回放.md)。八盘模式使用同一个原生 SSD pool 注册八个窗口。
