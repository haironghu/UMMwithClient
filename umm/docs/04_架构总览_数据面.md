# 架构总览：数据面（tier_router → transports → ssd_pool → 设备）

> 角色定位：真正搬运字节的那一层。`umm_read/umm_write` 的全部旅程。
> 代码：`umm/src/transport/` + `umm/src/memory_service/mem_service_direct.c`

---

## 1. 一次 umm_write 的完整旅程（RPC + tier 路由模式）

```
client 线程                                    物理落点
───────────                                    ────────
umm_write(desc, off, len, buf)
  │ desc.base_gpa = node|tier|offset
  ▼
tier_router.put(gpa)          ── 按 GPA 的 tier 位域分派
  ├─ tier=CXL → local transport ──────────────────────► client 进程 malloc 内存
  │                （memcpy，P0 锁收窄后真并行）
  └─ tier=SSD → ssd_transport_put
                   │ offset_in_pool = gpa_to_offset(gpa)
                   ├─ map_device() 成功 → memcpy ──────► 文件后端 mmap 页
                   └─ map_device() 失败（libnvm 无 mmap）
                      → mem_vtbl->ssd_write
                         │ 锁内仅取 pool 指针（P0 式收窄）
                         ▼
                      ssd_pool_pwrite(pool, voff)
                         │ 跨设备自动分段（ssd_pool_io）
                         ▼
                      ssd_backend_pwrite ── libnvm 后端
                         │ 选 ctx 槽位（轮询+每槽互斥锁）
                         │ 按 max_io(128KB) 再分段
                         ▼
                      nvm_host_write(ctx, buf, chunk, base_off+off)
                         │ bounce buffer + DMA
                         ▼
                      NVMe 盘 [窗口 base_off, base_off+capacity)
```

**关键事实**：RPC 模式下 umms 只做**分配**（返回偏移），数据不经过 umms；
SSD 设备被 umms 与 client **各自打开**（服务端管位图，客户端管 I/O）。

## 2. SSD 池（ssd_pool.c，896 行）

多设备虚拟地址空间 + 位图分配：

```
虚拟空间  [0, Σcapacity)
          ├─ dev0: [0, cap0)            → backend0（文件或 libnvm）
          ├─ dev1: [cap0, cap0+cap1)    → backend1
          └─ ...
I/O 路由：ssd_pool_io 按设备边界自动把一次 I/O 切成 ≤设备剩余 的若干段，
          分别路由到对应 backend（页粒度 4KB 位图仅用于分配，I/O 不查位图）
```

- 分配：`ssd_pool_alloc(size)` → 虚拟偏移（服务端调用）；
- I/O：`ssd_pool_pread/pwrite(voff, len, buf)` → 分段路由（两端都用）；
- 容量必须显式给出（libnvm `disk_info` 无总容量字段，`capacity=0` 一律拒绝）。

## 3. 双后端

| | 文件后端 | libnvm 后端 |
|---|---|---|
| 设备路径 | 普通路径（ftruncate+mmap） | `libnvm:<ctrl>[@ns][+<base_off>]` |
| I/O 机制 | mmap + memcpy（页缓存） | dlopen `nvm_host_read/write`（同步） |
| 分段上限 | 无（全量 pread/pwrite） | `disk_info.max_data_size`（真机 128KB） |
| 用途 | 测试/CI/过渡 | **生产**（用户态 NVMe 驱动） |
| 依赖 | 无 | libnvm_host.so（软依赖，`UMM_LIBNVM_PATH`）+ LD_LIBRARY_PATH |

**窗口基址**（base_off）：spec 中 `+<off>` 后缀（支持 0x），所有 I/O 在窗口
内相对编址、落盘加 base_off——机制性避开 LBA0，生产**必须**带窗口。

## 4. libnvm 后端并发模型（当前形态）

```
ssd_libnvm_open
  ├─ nvm_host_init × UMM_LIBNVM_CTXS（默认 4，1-16）
  ├─ 每 ctx 一把互斥锁（不假设库线程安全，R6a 构造规避）
  ├─ 开机只读探针：逐 ctx 读窗口首块，剔除静默损坏（多 init 自损防护）
  └─ I/O：轮询选槽 → 持槽锁 → 分段循环 → 放锁
```

真机现状（重要）：**libnvm_host 同进程多 init 会破坏先建 ctx**
（Invalid namespace），故生产固定 `UMM_LIBNVM_CTXS=1`——并发收益待
"单 ctx 多队列"API。完整分析见 `R6_单队列并发安全性遗留问题.md`。

|---|---|---|
| 单流 128KB 写 | ~90-105µs（≈1.24 GB/s） | 同步 QD≈1，64 样本极差 <6µs |
| 单流 8KB 写 | ~42-54µs | |
| Python 侧 4KB 读 | ~255µs/条 | 含 ctypes+引擎簿记 |

## 6. 锁纪律（P0 以来的原则）

1. **I/O 不进锁**：任何锁内只做指针/状态解析，memcpy/pread/nvm_host_* 全部在锁外；
2. **每资源自锁**：libnvm 每 ctx 一锁（而非全局一锁），锁粒度 = 队列；
3. **位图锁仅分配期**：`ssd_pool_alloc/free` 持锁，`pread/pwrite` 无锁；
4. 新增通路评审红线：不得在长耗时操作（>10µs 级）期间持有共享锁。
