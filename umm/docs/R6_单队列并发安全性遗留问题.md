# R6：libnvm 单队列多线程并发提交安全性 —— 遗留问题全记录与路线展望

> 状态：**开放（已缓解，未根治）**　最后更新：2026-07-22
> 相关代码：`umm/src/transport/ssd_backend_libnvm.c`、`umm/src/memory_service/mem_service_direct.c`
> 外部依赖：同事项目 `NPU_Direct_Storage`（`libnvm_host.so` + `libnvm_helper` 内核模块，BaM 的昇腾移植）

---

## 1. 问题定义

UMM 的 SSD 数据面最终落到 `libnvm_host.so` 的同步接口：

```c
int nvm_host_read (nvm_host_ctx_t *ctx, void *data, size_t size, uint64_t ssd_offset, size_t *xferred);
int nvm_host_write(nvm_host_ctx_t *ctx, void *data, size_t size, uint64_t ssd_offset, size_t *xferred);
```

一个 `nvm_host_ctx` 对应 **一对 NVMe 队列（1 SQ + 1 CQ）+ 一个完成线程 + 一块 128KB 预注册 bounce buffer**。两个未验证的安全性假设构成了 R6：

- **R6a**：多个线程**同时**对同一个 ctx 调用 `nvm_host_read/write`（即并发向同一 SQ 提交命令），库是否安全？（SQ tail 推进、phase bit、doorbell 写、CQ 收割是否都有内部同步？）
- **R6b**：同一进程内**多次** `nvm_host_init` 建立多个独立 ctx（多队列并行），库是否支持？

**当前结论：R6a 未验证（不敢裸测）；R6b 已被真机实证为"不支持"（见 §3）。**

## 2. 为什么这个问题重要

KV cache 卸载场景（sglang/vllm）的读写天然是多线程高并发的。单队列同步语义的吞吐天花板实测为：

| 指标 | 实测值（真机，华为 A3 + CANN 8.5） | 条件 |
|---|---|---|
| 128KB 写延迟 | ~90-105 µs（64 样本极差 <6µs） | 同步单流，QD≈1 |
| 8KB 写延迟 | ~42-54 µs | 同上 |
| 4KB 读延迟（含 Python/ctypes） | ~255 µs | 串行基线 523ms / 2048 IO |
| 单流吞吐 | **≈1.24 GB/s** | 同步 128KB |

企业级 NVMe 通常有 3-6 GB/s 实力——**单队列同步模型只能吃到三分之一以下**。R6 不解，UMM 的并发引擎（ConcurrentIOEngine）对 SSD tier 只是"形式并发、实际串行"。

## 3. 来龙去脉（完整时间线）

### Phase 1-2（单 ctx 时代，一切正常）
- 每进程一个 ctx：测试程序 1 个、umms 1 个、client 1 个。
- 真机验证：INITONLY 冒烟 → 窗口 [1GB, 1GB+16MB) 内 8KB/512KB 写读逐字节一致。
- 此时并发提交问题**根本不存在**——所有 I/O 天然单线程到达 libnvm。

### Phase 3（服务集成打通，并发仍为"伪并发"）
- RPC 分配面 + client 本地 tier 路由数据面全链路 PASS。
- umms 与 client **跨进程**各持 1 ctx 同时操作同一控制器——正常。
  （这证明：驱动 `libnvm_helper` 与盘**可以**承接多队列并发，问题不在驱动也不在盘。）

### Phase 4 起点：真机实测并发 0.88x（不升反降）
- D2 场景：串行读基线 523ms vs 引擎 4 队列并发读 595ms。
- 排查坐实两处串行化点：
  1. **UMM 侧**：`memsvc_ssd_io` 持 mem_service 全局锁贯穿整个同步 I/O（~255µs）——所有线程在此排队。**已修复**（锁内仅解析 pool 指针，I/O 移出锁外，commit `44e875d`）。
  2. **libnvm 侧**：单 ctx 单队列——需要 ctx 池解决。

### ctx 池尝试：撞上"多 init 自损"（R6b 实证）
- 实现：后端启动时 `nvm_host_init` × 4，每 ctx 独立互斥锁，轮询分派。
- 真机结果：**第一个写即失败**——`sc=0xb (Invalid namespace or format)` + completion 超时，且失败的是**最先创建**的 ctx。
- 推断：第 2/3/4 次 init 重置了**进程级全局控制器状态**（疑控制器复位或 namespace 重新 attach），先建 ctx 的队列随之失效。init 成功 ≠ 可用。
- 桩库（文件模拟）无此行为——容器验证全部通过，**只有真库暴露**。

### 当前缓解（生产安全形态）
1. `UMM_LIBNVM_CTXS` 默认 4，但 open 时对每个 ctx 做**只读探针**（读窗口首块，零写入）：探针失败的 ctx 告警剔除，全灭则 open 直接报错——静默损坏变为启动期可见/自愈降级（commit `5c30ddb`）。
2. 每 ctx 一把互斥锁：不依赖 libnvm 内部线程安全性（R6a 由构造规避）。
3. 真机运行固定 `UMM_LIBNVM_CTXS=1`：与 Phase 1-3 行为完全一致，吞吐上限 ~1.24 GB/s。

## 5. 展望：单 ctx 多队列路线（推荐投入方向）

### 5.1 为什么不选"修复多 init"
多 init 自损的根因是库内**进程级全局控制器状态**（BAR 映射、admin 队列、ns 状态）。修复它等于做一次全局状态隔离重构，风险高（我们刚被这类静默损坏咬过一次）、工作量大（预估中改 1-2 周，大改 2-4 周），且收益与多队列方案相同。

### 5.2 建议 API 草案（提给 libnvm 提供方）

```c
/* 现有接口不变：nvm_host_init 建控制器上下文（全局一份） */

/* 新增：在同一控制器上创建第 N 对 I/O 队列 */
int  nvm_host_qp_create(nvm_host_ctx_t *ctx, size_t queue_depth, nvm_host_qp_t **qp);
void nvm_host_qp_free(nvm_host_qp_t *qp);

/* 新增：指定队列的同步 I/O（语义同 nvm_host_read/write） */
int  nvm_host_read_qp (nvm_host_qp_t *qp, void *data, size_t size,
                       uint64_t ssd_offset, size_t *xferred);
int  nvm_host_write_qp(nvm_host_qp_t *qp, void *data, size_t size,
                       uint64_t ssd_offset, size_t *xferred);
```

理由：
- **符合 NVMe 模型**（一控制器多队列对），不碰全局状态雷区；
- 底层能力现成（F6），预估工作量 **3-5 天**：封装内部建队函数 + 每 qp 独立 completion 等待/收割；
- 驱动 1024 qp 余量（F1），我们只要 8-16 对。

### 5.3 UMM 侧适配（已基本就绪）
- `ssd_backend_libnvm` 的"槽位"语义从 ctx 换成 qp：dlopen 时探测 `nvm_host_qp_create` 符号——**有则走多队列，无则回退单队列**（向后兼容，零部署成本）；
- 每槽互斥锁、轮询分派、开机探针逻辑原样复用；
- 配置不变：`UMM_LIBNVM_CTXS` 语义变为"队列对数"。

### 5.4 预期收益与验证计划

| 队列对数 | 预期并发读加速比（对照基线 0.88x） | 验证方法 |
|---|---|---|
| 1 | 1.0x（对照组） | demo_e2e_ssd.py D2 |
| 4 | 2.5-3.5x | 同上，`UMM_LIBNVM_CTXS=4` |
| 8 | 4-6x（或触及盘/Python 瓶颈） | 同上 + C 级微基准隔离 Python 开销 |
| 16 | 找饱和点 | C 微基准 + soak 30min |
