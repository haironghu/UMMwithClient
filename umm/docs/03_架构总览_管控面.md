# 架构总览：管控面（ummD + umms + RPC 协议 + 配置）

> 角色定位：集群的"控制塔"。负责 **chunk 元数据**（ummD）与**存储分配**
> （umms）两件控制面事务；**不接触数据面**（数据面见 04 文档）。

---

## 1. 双服务分工

```
                ┌──────────────────── 客户端进程 ────────────────────┐
                │  libumm（RPC client：meta_rpc_* / mem_rpc_*）       │
                └──────────┬───────────────────────┬─────────────────┘
                  meta 协议 │ TCP 20001     mem 协议 │ TCP 20002
                           ▼                       ▼
                ┌──────────────────┐    ┌───────────────────────────┐
                │ ummD（元数据服务） │    │ umms（内存服务）           │
                │ meta_server.c    │    │ mem_server.c              │
                │ · chunk 名→描述符 │    │ · CXL/DRAM 池（位图）      │
                │ · 引用计数        │    │ · ssd_pool（分配权威）     │
                │ · 存储拓扑注册表  │    │ · alloc/free[_tiered]     │
                └──────────────────┘    └───────────────────────────┘
```

| 服务 | 可执行 | 底层实现 | 持有状态 |
|---|---|---|---|
| ummD | `bin/ummd`（meta_server.c + meta_service_direct） | 哈希表（meta_hash_table.c） | chunk 元数据、refcount、**各节点存储拓扑** |
| umms | `bin/umms`（mem_server.c + mem_service_direct） | 位图分配器 + ssd_pool | CXL 内存池、SSD 设备池（**分配权威**） |

**当前局限**：两服务互相独立——umms **不会**主动向 ummD 上报拓扑
（topology 目前由 client 经 `umm_register_storage_tier` 上报，见 §4）。
服务间无心跳/租约，单节点场景够用，多节点生产化需补。

## 2. RPC 协议

帧格式（src/protocol/protocol_common.c）：`magic | op | body_len | body`。
序列化全部走 `proto_write_*/proto_read_*` 手工对齐（整数转网络序，结构体
逐字段展开——**无 padding 风险**）。

### meta 协议（meta_protocol.h，client ↔ ummD）
| op | 用途 |
|---|---|
| REGISTER/LOOKUP/UNREGISTER_CHUNK（1-4） | chunk 元数据生命周期 |
| ADD_REF / RELEASE_REF（5-6） | 引用计数（共享 chunk） |
| LIST_CHUNKS_BY_NODE（7） | 按节点枚举 |
| HEARTBEAT（8） | 存活探测 |
| **REGISTER_STORAGE_RESOURCE（9）** | 节点上报 SSD 资源（Phase 3 接通） |
| **GET_STORAGE_TOPOLOGY（10）** | client 查询节点拓扑 |

### mem 协议（mem_protocol.h，client ↔ umms）
| op | 用途 |
|---|---|
| ALLOC / FREE（1-2） | CXL 池分配/释放（legacy） |
| **ALLOC_TIERED / FREE_TIERED（5-6）** | 按 tier 分配/释放（SSD 走这里） |
| GET_[TIER_]STATS（3,7） | 池统计 |
| REGISTER_STORAGE（8）/ GET_TOPOLOGY（9） | 服务端池管理/查询 |
| **DATA_READ / DATA_WRITE（10-11）** | **Phase 1 新增：跨节点数据面**。req body = gpa(u64)+len(u64)，payload 流式跟在帧后（不占 4KB body，上限 `data_max_io`，缺省 1MB）。仅服务 SSD tier GPA，由属主节点对本盘执行 I/O |

**契约变更（Phase 1，2026-08）**："RPC 仅控制面"原则自此扩展——
mem 协议新增 DATA_READ/DATA_WRITE 两个数据面 op，供**非属主节点**的客户端
经 `transport_remote` 访问远端 SSD。本节点数据面仍不走 RPC（路径不变）。
配套变更：
- `ALLOC_TIERED` 响应从 12 字节扩为 **13 字节**（末字节 = 属主 node id）；
  按 body_len 向后兼容（旧服务端 → 客户端回退 `ssd_owner_node` 配置）。
- 逐请求鉴权：header `reserved[6]` 携带 `rpc_token` 的 FNV-1a 摘要低 6 字节；
  服务端配置 token 后校验失败**直接断连不回响应**。全 0 = 未启用（旧线格式）。
- accept 侧 IPv4 CIDR 白名单（`allow_cidrs`），不在表内连接即断。

设计与部署细节见 `../docs/05_多节点远程数据面_规划与Phase1设计.md`。

## 3. 拓扑流（Phase 3 接通的关键链路）

```
client: umm_register_storage_tier(SSD, "libnvm:...", cap)
   │ ① meta_rpc_register_storage_resource ──► ummD 记录 node→topo
   │ ② 本地重建 tier_router（含 SSD transport）——数据面就绪
   │
其他 client: umm_init → meta_rpc_get_storage_topology ──► ummD 返回 topo
   └── configure_transports_from_topology：按 topo 建本地 SSD transport
```

**已修复的两个布局 bug（Phase 3）**：
1. ummD 内部按 tier 稀疏存放拓扑，但线协议 pack 从 `resources[0]` 连取
   `num_resources` 项——稀疏布局导致真实资源丢失。现 ummD 对外返回
   **紧凑数组**；
2. client 侧 `configure_transports_from_topology` 原先只遍历前
   `num_resources` 项，改为遍历全部 tier 槽位并过滤 online（稀疏/紧凑
   两种布局都兼容）。**遍历拓扑的正确姿势：全槽位 + online 过滤**。

## 4. 配置体系

umms 支持 `-c config.yaml`（简化 yaml 解析，config_parser.c）+ 命令行
（命令行先解析，配置文件后覆盖）。**配置键全表**：

| 键 | 含义 | 示例 |
|---|---|---|
| `node_id` | 本节点 ID | 0 |
| `listen_addr` / `listen_port` | 绑定地址/端口 | "0.0.0.0" / 20002 |
| `memory_size` | CXL/DRAM 模拟层容量（字节） | 134217728 |
| `base_gpa` | CXL 池基址 | 0 |
| **`ssd_devices`** | SSD 设备列表 `"path:size,..."`（G/M/K 后缀） | 见下 |
| `meta_server_addr` / `mem_server_addr` | （client 侧配置）服务端地址 | "127.0.0.1:20001" |
| `transport` | client 传输后端（""=tier 路由 / "mock"） | "" |

**生产 SSD 配置（config/umms_ssd_libnvm.yaml 模板）**：
```yaml
ssd_devices: "libnvm:/dev/libnvm_helper0@1+0x40000000:16G"
#            └ctrl 路径      └ns └窗口基址(1GB) └窗口容量
# 窗口语义：落盘偏移 = base_off + 池内偏移，机制性避开 LBA0
```

## 5. 启动顺序与依赖

```
1) ummD 先行：  ./bin/ummd -p 20001 -b 0.0.0.0
2) umms 随后：  ./bin/umms -c config/umms_ssd_libnvm.yaml
                （libnvm 设备需先 export UMM_LIBNVM_PATH + LD_LIBRARY_PATH）
3) client 连接：meta_addr=ummD 地址, mem_addr=umms 地址
```

**依赖项**：两服务仅依赖 pthread + libc；SSD 设备打开失败 umms 启动即报错
（端口不监听），client 拓扑为空时优雅降级（CXL-only）。

## 6. 管控面已知边界

1. **ummD 拓扑无持久化/租约**：进程内存态，重启即丢（client 重注册即可）；
2. **umms→ummD 自动上报缺失**：多 client 场景目前要求各 client 自行
   `enable_ssd`（幂等，可重复）；
3. **无鉴权/加密**：RPC 明文，限可信内网；
4. **无 per-device 放置**：`MEM_OP_ALLOC_TIERED` 只按 tier 分配，不能指定
   池内具体设备（VirtualMedia 需要，属已知缺口）。
